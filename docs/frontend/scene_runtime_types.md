# 场景制作共享契约整理

状态：设计整理，待实现。本文收敛此前类型草案、实际源码和接入审计中的分歧；本轮只修改文档，不修改运行代码、不改写模型场景、不启动模型调用。

实际运行类型仍在[types.ts](../../tools/scene-pipeline/types.ts)，现有对象检查在[contract.js](../../tools/scene-pipeline/contract.js)。下面明确标为“拟统一”的内容尚未落地，不可据此声称旧产物已经符合新约定。本文件替换此前文档中的并行类型写法，不增加案件修订号或版本分支。

目标：让模型看到的约定、生成代码的交付物、运行器执行的能力、检查器拒绝的条件和前端展示的结果能够逐项对应。

## 1. 三个组件与一份共享契约

| 组件 | 职责 | 内容来源 |
| --- | --- | --- |
| 制作运行器 | 准备原始输入、调用模型、保存结果、安排校验和修正、管理任务 | 通用程序 |
| 浏览器运行器 | 加载已检查代码、使用Three.js绘制、执行登记动作、拍摄实际画面 | 通用程序 |
| 部件与组装器 | 创建具体几何，决定布局、材质、灯光，登记节点、绑定和视角 | DeepSeek |
| 检查器 | 解码交付物，检查代码能力、引用、实际对象与声明，并输出具体问题 | 通用程序 |
| 视觉与整体审核 | 根据原始字段和实际截图判断事实、支撑、附着、净空及整体合理性 | DeepSeek独立上下文 |

共享契约包含三层：

1. **结构定义**：字段、引用、坐标、输入输出类型。
2. **执行规则**：对象身份、直接父子关系、动作语义、允许的代码能力。
3. **诊断规则**：哪里违反哪条约定，怎样把证据交给模型修正。

具体房间的尺寸、陈设、部件代码、组装器和修正仍由DeepSeek完成。通用检查器不得替模型移动物体、重接父节点、补造绑定或删除报错代码。

## 3. 共享定义放在哪里，怎样被引用

以下为拟实施职责，先复用现有目录，不另建通用代理框架：

| 位置 | 整理后的职责 |
| --- | --- |
| `tools/scene-pipeline/schemas.ts`（拟补） | 可序列化数据的结构定义和运行时解码，类型从结构定义推导 |
| `tools/scene-pipeline/types.ts` | 引用上述数据类型；补充只能存在于内存中的Three.js对象与函数签名 |
| `tools/scene-pipeline/contract.js` | 对象身份、引用、树、动作等交叉检查；返回统一报告 |
| `tools/scene-pipeline/code-policy.mjs`（拟补） | 代码能力规则、稳定规则ID及面向模型的约束说明 |
| `tools/scene-pipeline/prompts.mjs` | 引用真实类型和能力规则，组织通用任务提示，不再手写另一份限制清单 |
| `tools/run_scene_pipeline.mjs` | 调度这些公共能力，保存、转发报告；不自行复制一套交付物判定 |
| `tools/scene-pipeline/runtime.js` | 使用同一份运行时契约加载、绘制、应用动作、截图 |
| 后端`sceneproduction`与前端API | 使用约定的JSON视图；Scala与TypeScript通过同一组边界样例核对编解码 |

可复用项目已有Zod描述JSON形状，TypeScript类型由其推导。Node与浏览器消费同一来源产生的运行时定义；不能让浏览器直接加载未构建的`.ts`。具体构建接入沿用现有工具链，落地时明确导出入口。

Scala不能直接导入TypeScript。后端只接收其负责的JSON状态、权限与成品记录，不接收`THREE.Object3D`；跨语言边界用共同JSON样例验证字段、枚举、空值和错误结构，避免为了“统一类型”强行统一语言或把对象树送进数据库。

保留生成JavaScript的方式。模型得到与检查器一致的类型说明；静态类型检查可使用只读的类型上下文或JSDoc引用，随后仍需运行时校验。禁止运行时`import`与允许注释中的类型引用应明确区分。TypeScript断言不作为验收依据。

## 4. 先区分编号，不从名字猜关联

| 编号 | 表示什么 | 谁定义 |
| --- | --- | --- |
| `SceneObjectId` | 本场景需表达或核对的物件／对象 | 作者字段，或模型有来源地提出并经审核确认 |
| `EntityId` | 已有案件领域中的实体 | 复用后端已有定义，不由组装器猜造 |
| `ModuleId` | 一份可重复调用的部件代码 | 模型计划 |
| `InstanceId` | 该模块的一次实际构建 | 模型计划 |
| `LocalNodeKey` | 某个部件对外提供的本地节点名 | 模型计划的模块交付约定 |
| `SceneNodeId` | 组装后登记的一个真实节点 | 模型组装器，按共同命名／分配约定生成 |

例如场景物件`object_a`可以由`module_a`的`instance_a`中一个局部节点表现；四者不因名字相似就自动相等。需要跨模块引用时使用完整引用：

```ts
type LocalNodeRef = Readonly<{
  instanceId: InstanceId;
  nodeKey: LocalNodeKey;
}>;
```

JSON中这些编号仍是字符串；通过解码器和索引核对，不能只换一个TypeScript类型名。对象名称、模块名、案件时代等开放语义不做封闭枚举。

### 4.1 作者字段索引

原始输入完整保留，模型直接读取。程序只为关联建立索引，不把助手转述替换成原始描述：

- 来源文档ID和字段指针；引用必须能定位，找不到时列缺口。
- 场景物件目录：`objectId`、来源引用、可选的已有`entityId`。
- 每项物件的表达要求：必须有节点、允许非几何表达，或待补充。理由明确，不能把未画出当成事实不存在。

作者已有稳定ID时保留。若输入只有自然语言，由模型提出物件目录并引用原字段；程序核对结构和引用，作者在布局阶段一并查看。程序不从“床”“桌子”等关键词擅自认定实体或补造线索。

当前样例的`sceneObjects`不是后端`EntityId`目录，整理时必须保留这个区别。

## 5. 模型计划与模块交付

`ScenePlan`保留当前的`modules[].specs[]`和`instances[].module/specIndex/placement`。在此基础上补齐明确的交付约定，而不再增加另一套实例参数写法。

每份规格应记录：

| 内容 | 约定 |
| --- | --- |
| `parameters` | 开放JSON，由模型决定；与原始事实、制作选择区分 |
| `sizeBudget` | 初始姿态外包尺寸，包含附属几何；不是房间内尺寸 |
| 节点端口清单 | 本规格必须交付哪些`LocalNodeKey`，供哪些绑定或动作使用 |
| 锚点端口清单 | 锚点键、所属节点键、点坐标的参照节点 |
| 来源与要求引用 | 使用哪些作者字段，承担哪些场景要求 |

拟补的字段统一使用下面的名称，避免落地时再产生不同说法：

```ts
type ModulePorts = Readonly<{
  nodeKeys: readonly LocalNodeKey[];
  anchors: readonly { key: string; nodeKey: LocalNodeKey }[];
}>;

type ModuleBuildInput = Readonly<{
  parameters: JsonValue;
  sizeBudget: { widthMeters: number; heightMeters: number; depthMeters: number };
  ports: ModulePorts; // 拟新增，属于每份spec，支持同模块不同规格
}>;

type PlannedObjectBinding = Readonly<{
  objectId: SceneObjectId;
  targets: readonly LocalNodeRef[]; // 非空
}>;
```

`ports.nodeKeys`必须包含`root`；`ScenePlan`拟增加`objectBindings: readonly PlannedObjectBinding[]`，实际输出的`SceneDefinition.bindings`使用第7节的全局节点映射。以上名称属于待实施定义，不是当前源码已有字段。

根端口统一为`root`。计划必须明确：哪些`SceneObjectId`由哪个`LocalNodeRef`表现；同一物件可对应多个节点，但每个目标必须真实存在。装饰可以没有案件实体关联。

必须表达的物件漏交、引用不存在的实例、端口缺失，都要阻断并反馈，不能像目前的`addBinding`一样找不到就静默跳过。

模块验收先于组装：检查返回形状、根姿态、节点归属、节点身份和已声明端口。未通过的部件不能直接以“有一个JS文件”作为成功交付。

## 6. 部件根、节点身份与真实树

`BuiltModule`沿用现有的普通对象映射，拟统一的身份要求如下：

```ts
// 表达交付含义的示意；可序列化字段以共享schema为准。
type BuiltModule = Readonly<{
  root: THREE.Group;
  nodes: Readonly<{ root: THREE.Group } & Record<LocalNodeKey, THREE.Object3D>>;
  anchors: Readonly<Record<string, {
    nodeKey: LocalNodeKey;
    pointMeters: Vec3;
  }>>;
}>;
```

必须满足：

1. `built.nodes.root === built.root`，初始根为单位姿态。
2. 除`root`外，登记节点都属于该根的后代；节点键不指向无关对象。
3. 一个对象只使用一个登记节点键。语义名称需要共享同一对象时，通过多个物件绑定引用这个节点，不给同一对象重复登记多个节点ID。
4. 一个模块被调用多次时，各实例的可移动对象独立，不共享同一对象树。
5. 模型可自行决定内部几何和分组；交付端口必须与计划一致，修改端口要同步所有引用并重新检查。

最简单的装配方式是将`built.root`作为实例根，应用`placement`后挂到场景根。`placement`只能应用一次。

模型若确需额外包装层，必须明确登记真实层级：

```text
场景根（不进入nodeObjects）
  └─ 实例包装节点（如确有必要）
       └─ built.root（仍是root端口对应的对象）
            └─ 部件内部节点
```

包装节点不能冒充`built.root`，不能把`root`端口重定向到包装节点。所有登记节点与场景根之间必要的中间父节点都应登记；普通装饰叶网格不必逐一登记。

`SceneNodeDefinition.parentId`始终表示**实际直接父节点**。只有直接父节点确为场景根时才写`null`；不能用最近的已登记祖先代替直接父节点，也不能跳过未登记中间层。

诊断中“实际父节点是场景根”和“实际父节点未登记”需要分别表达；不能都显示成`actual: null`，让模型误判。

## 7. 场景定义、物件绑定与动作

`SceneAssembly`保留：

- `root`：Three.js场景根，单位姿态。
- `nodeObjects`：全局节点ID到实际对象的普通对象映射。
- `definition`：可保存的JSON声明，不能包含Three.js对象引用。

`definition`保留节点、锚点、动作、要求、视角及`appearance`。节点ID与`nodeObjects`逐一对应，禁止多ID登记同一对象。

### 7.1 拟统一物件绑定

绑定统一落到`SceneObjectId`目录，再通过目录中的可选`entityId`与后端案件实体关联：

```ts
type SceneObjectBinding = Readonly<{
  objectId: SceneObjectId;
  nodeIds: readonly SceneNodeId[]; // 非空，逐项检查
}>;
```

这将替换当前`nodeId/entityId`绑定的直接含义，属于待实施的协议调整。迁移时要一起修改类型、模型说明、检查器和消费者，不能只改提示词，或同时把同一个字段解释成两种ID。

检查包括：目录目标存在、节点存在、必需物件完整覆盖、无虚构对象ID、多个绑定是否符合计划。几何覆盖范围是否合理仍由视觉核对。登记绑定不等于玩家取得线索。

### 7.2 保留既定坐标和动作语义

- 米制、Y向上、部件正面为本地+Z。
- 节点姿态相对于实际直接父节点；场景根作为世界坐标原点。
- 欧拉角为XYZ顺序、弧度；正尺寸和缩放、所有数值有限。
- 平移使用`closedPositionMeters/openedPositionMeters`，旋转使用`closedRotation/openedRotation`，由`kind`明确区分。
- `space`为`parent-local`，端点为绝对本地值；重复应用同一状态不累加。
- 平移只改位置，旋转只改旋转；转轴来自真实节点原点，旋转不清零门轴位置。
- 初态与对应通道端点一致，同一节点同一通道只登记一个动作。

目前先做制作预览。后续接玩家操作时，通过显式后端操作ID关联这些表现，不让模型代码授予权限或改写知识。

## 8. 支撑、附着、净空与视觉要求

继续采用已讨论的边界：父子树表达坐标继承；支撑、附着、空间连接和净空以`SceneRequirement`引用节点、来源及自然语言关系，交给视觉模型结合实际画面判断。

不新增复杂的两两距离系统或物理求解器，不把包围盒相交直接视为穿插，也不把两个锚点坐标相同视为已固定。原始字段明确给出的距离、数量、相对位置仍必须保留。

每个要求有来源或明确的制作选择依据。来源引用必须可解析，关键要求必须进入审核清单，不能仅有一条笼统的“整体合理”要求就算完整覆盖。无法看清时要求补视角，不补造肯定或否定事实。

`SceneViewpoint`沿用世界相机位置／目标、隐藏节点和动作目标状态。每次截图从一致初态复位，至少提供当前策略要求的整体及关键关系视角；数量不代替覆盖检查。

## 9. 代码能力与类型说明必须一致

运行时数据类型无法表达“禁止某种JavaScript语法”。因此能力规则单独维护，但提示词和检查器必须引用同一份规则目录。

| 规则层次 | 检查内容 | 失败时交给模型 |
| --- | --- | --- |
| JavaScript语法 | 是否能被目标运行环境解析 | 实际解析错误、文件、行列、片段 |
| 宿主能力限制 | 当前禁止的`while/do/import`、动态导入、受限全局访问等 | 明确规则ID、语法种类、位置和允许方式 |
| 函数交付 | `buildAsset`或`assembleScene`的导出及返回协议 | 期望签名、实际导出或返回值形状 |
| 对象与引用 | 树、端口、绑定、动作、相机等 | 具体对象ID、期望和实际值 |

本次整理不改变当前允许的代码集合。现有`while`禁用规则是否应该保留，另行评估；在做出调整前，必须如实告诉模型它被禁止，不把合法JavaScript错误地称为语法非法。

对标识符访问与对象字段名分别判断，避免把正常字段名误当成访问浏览器全局变量。规则目录需要有与检查器对应的例子和反例；禁止项的增删必须同时更新模型约束与检查测试。

代码筛查只检查明确定义的条件，不宣称是完备的不可信代码沙箱。不增加针对某个案件的代码替换或自动几何补丁。

## 10. 统一错误报告与模型修正输入

现有`CheckIssue`的`stage/code/severity/target/expected/actual/files`作为基础，补齐定位和证据，统一计划、代码、对象、视觉和整体检查的公共字段：

```ts
type SourceLocation = Readonly<{
  file: string;
  line: number;     // 从1开始
  column: number;   // 从1开始
  snippet?: string;
}>;

type CheckIssue = Readonly<{
  stage: 'protocol' | 'runtime' | 'geometry' | 'visual' | 'overall';
  code: string; // 程序能处理的检查码由共享目录登记
  severity: 'blocking' | 'minor';
  message: string;
  target: {
    moduleId?: ModuleId;
    instanceId?: InstanceId;
    nodeId?: SceneNodeId;
    objectId?: SceneObjectId;
    motionId?: MotionId;
    requirementId?: RequirementId;
  };
  locations: readonly SourceLocation[];
  expected?: JsonValue;
  actual?: JsonValue;
  evidence: string;
  adjustment?: string;
  files: readonly string[]; // 目标产物ID，如模块ID或assembler，不是任意写入路径
  screenshotIds: readonly string[];
}>;
```

本段为拟统一字段示意，不能再由各消费者各抄一份。空数组／可选字段的编码方式在共享schema固定，Scala往返样例需一致。

例：拒绝某条循环时，至少提供`unsupported_construct`、`WhileStatement`、源文件行列和片段，说明宿主当前禁止该构造以及允许的有界迭代方式；不只返回`unsupported construct`。父子错误需要指出实际直接父节点的身份，区分场景根和未登记节点。

`CheckReport`按阶段记录通过、失败或无法确认，关联本次产物及截图。程序错误由检查器填充，不让模型自行改成通过；视觉审核意见按同一公共结构解码，关键不确定项阻断通过。

模型修正请求必须包含：

- 原始字段和已经确认的计划；
- 当前公共类型与能力规则；
- 完整结构化问题；
- 待修文件原文及相关部件／组装器；
- 适用的实际截图和视角；
- 剩余预算及明确的返回格式。

修正由DeepSeek返回完整替换文件，再经过相同检查。重复错误比较规则码、目标和实际值，不能只比较一句错误文本，也不能一律默认修组装器。

模型供应商失败继续使用已有`ModelFailureCode/ModelRequestFailure`，归属调用层，不伪装成场景语法问题；与当前产物关联后展示安全摘要。密钥、供应商原始错误正文、私有凭证和未验收代码不下发普通页面；有界完成片段仅保存在私有诊断记录。

前端作者问题视图应保留规则码、目标、定位、期望与实际值，允许逐步展开；不再只压缩成“文字＋严重程度”。

## 11. 任务状态、预算与恢复

数据库`Draft/Queued/Saved`表达作者资料和成品生命周期；运行器阶段表达制作执行进度。这两个维度可以保留，需有明确的有效组合，不把它们误当成两份互相竞争的完整状态。

| 权威归属 | 保存什么 | 允许做什么 |
| --- | --- | --- |
| 后端／数据库 | 作者归属、冻结输入、生命周期、用户确认和明确的执行授权 | 鉴权、短事务、允许启动／继续／保存的判定 |
| 制作进程 | 当前执行阶段、调用和修正记录、检查结果、产物与失败现场 | 根据共同策略执行已授权步骤，记录实际结果 |
| 前端 | 任务定位与展示状态 | 依据服务端动作前提展示按钮；不自行授予运行权限 |

布局确认应成为有持久化依据的制作授权，绑定具体计划内容；不能只凭任意文件存在就视为某个新计划也已获确认。保存成品必须对应同一份已通过检查的代码、计划和截图。仅有`passed: true`不能替代证据一致性。

阶段名称、终止条件、可恢复条件和UI按钮前提统一描述。限额由单一策略入口决定，后端和前端读取有效值，避免各自硬编码10与88。

本次不变更当前10处理轮、88次调用上限，不重置已用次数，不把它们称为10次视觉审核。保留生成调用、修正、运行检查、视觉审核、整体复核各项计数。若需要按阶段重分预算，另行讨论，不能在整理契约时悄悄放宽。

调用预算在发出请求前占用，并记录请求是否实际发出、响应是否收到。一次修正可能包含多文件和多次模型请求，检查尝试也不等于截图成功，不能简单把各项计数相加当成调用总数。供应商未返回用量时标记未知，不把缺失用量说成确定没有消费。

显式恢复应区分：未发送、发送结果不确定、返回已保存、返回已通过代码检查、运行通过、审核通过。每一步需要的证据不同；不靠文件存在就认定成功，不自动重发结果不确定的付费请求。

复用完整模型返回前，核对原始字段、确认计划、模块输入，以及当时实际系统提示／类型／能力约束是否与当前一致；目前只比较用户载荷的方式不够。即使允许复用，也须按当前规则重新检查。通过实际内容与证据核对，不引入案件修订号、版本号或按编号切换逻辑。

## 12. 迁移顺序与验收边界

按下面顺序替换旧定义，避免新旧含义并行：

1. **固定边界定义**：确认四类对象身份、部件端口、根节点身份、绑定目录与错误字段；对照现有源码列出字段变更。
2. **提取共同来源**：结构、类型、能力规则各有一个入口；提示词、检查器、模型修正和前端视图引用它们，删除重复清单。
3. **先验部件再验组装**：补齐完整物件映射检查、模块端口检查、根／别名规则及真实直接父子检查。错误反馈不改写生成代码。
4. **统一任务投影**：对齐后端、Node和前端的状态组合、限额、恢复与证据要求。
5. **验证真实链路**：离线边界通过后，经明确授权再恢复真实模型任务，直到运行、实际截图、视觉和整体审核完整通过；主站保存与重启恢复最后核对。

至少覆盖这些验收样例：

| 样例 | 必须产生的结果 |
| --- | --- |
| 字段、单位、实例引用或端口不存在 | 在对应交接阶段给出具体错误，不静默跳过 |
| 多个名称登记同一个根对象 | 部件阶段拒绝，避免拖到组装后循环修正 |
| 合理的未登记装饰叶网格 | 允许；不强制把所有三角网格都变成业务节点 |
| 包装节点、部件根、内部活动节点 | 真实直接父子关系一致；中间层不能折叠冒充 |
| 必需物件绑定漏掉／实体ID混成实例ID | 明确失败，即使剩余绑定均合法也不能通过 |
| 禁止构造与真正语法错误 | 反馈种类、文件、行列及源片段，类型和消息不同 |
| 非零门轴、旋转／平移重复应用 | 保留其他通道，不发生累计偏移 |
| 结构正确但支撑／净空无法确认 | 交实际多视角审核，不从类型正确推定合理 |
| 网络失败、失败刷新、重复继续、进程重启 | 保留原记录；不重复发起付费请求，不伪造完成 |
| 旧回答的提示词或执行约束已经不同 | 不盲目复用；保留记录，按当前契约重新核验 |
| 作者私有资料和玩家视图 | 权限隔离；制作信息不自动进入玩家知识 |

当前真实任务仍保留原记录，不因为本文整理而删除、不擅自修正、不将其改记为通过。本文完成表示契约已整理到可审阅程度，尚不表示共享实现、生成质量或玩家调查接入已完成。
