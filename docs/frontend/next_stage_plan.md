# 整案跑通后的实现方案

规划日期：2026-10-31，实施更新：2026-11-01。规划基线：`vicarage_study/20`、`study/5`；整案已由用户跑通。用户已授权按顺序推进，A批发布为修订21，B批网站入口与调查恢复已落地（见[实现记录](implementation.md)），C—E仍为待实现方案。C已按用户最新要求改为连续问询，取消首轮／补充阶段入口；下文A、B保留历史实施设计，已完成情况以实现记录为准。

## 1. 目标与实施顺序

先整理已经能玩的首案，再把网站从单案演示改成有案件入口的侦探剧场。保留玩家发现、追问和推理的空间，减少重复证据、预设答案及操作门槛造成的困惑。

| 批次 | 交付内容 | 原因与范围 |
| --- | --- | --- |
| A：首案整理 | 移除时间核对表；整理材料、出示与回应；明确补充问询入口 | 直接处理本次试玩问题，形成干净的首案体验 |
| B：入口页与案件区 | 首页、案件列表、案件详情、开始／继续调查、本人调查列表 | 用户下一项主要功能；先放一个真实可玩的案件，为后续案件复用 |
| C：连续问询与说法记录 | 统一入口，取消手动阶段；模型结合实际材料连续回应，保存说法变化 | 首案优先，复用现有模型与事务；真实语义验收后交付 |
| D：现场探索补强 | 小型树林探索、亲手发现晶体，再申请专业辨认 | 落实玩家发现线索的方向，控制美术规模 |
| E：用户案件上传 | 模板、草稿上传、校验、私有试玩、发布流程 | 在案件区和通用启动能力稳定后逐步开放 |

建议按A→B→C→D推进；E先形成格式与一份开发用样例，再做用户上传。若课程时间只够两批，优先交付A、B，明确展示其余能力的实际状态，不用无效按钮冒充完成。每批独立验证和提交；不预先承诺工期或某次修订编号。

## 2. A批：移除时间核对，整理证据表达

### 2.1 移除独立时间核对功能

删除新调查中的“我的时间核对”表单、提交入口及“阶段完成·书房初查”这一局部完成提示。检查座钟、询问牧师习惯、向玛丽核实报时依据仍正常取得原始材料；时间冲突由玩家自己发现，可以在问询和最终推理中讨论。

不把时间核对改成另一道必填表，不要求先通过算时题才能进入补问或结案，不自动生成“正确的时间结论”。继续使用现有推理评审，依据实际解释与引用讨论时间，而非强制18:07作为全案唯一答案。

实施时需处理三处关联：

- 前端：移除新修订的表单、草稿状态和提交调用，线索页专注材料与证词对照；更新简介、阶段提示及指南。
- 后端与作者配置：用新修订取消比较规则和结果材料，检查所有材料前置、复盘关联、模型披露和阶段投影，不能只隐藏按钮后留下无解条件。
- 旧调查：保留历史核对笔记、原请求及回执。旧接口仅服务原修订恢复与重试，不再作为新调查入口；旧调查可以查看原有内容，不自动迁移或删除。

这需要让阶段展示不再强制依赖一条“完成材料”；不应为了填满旧字段而虚构一份新线索。

### 2.2 材料、出示动作、人物回应分开

当前材料中混有“取得的信息”“向谁出示过”和“对方对此作出什么回应”。只删“向玛丽出示”几个字，可能留下多份同名材料，也可能把不同内容误合并。因此先逐条核对正文和用途，再整理。

| 情况 | 新的展示与记录方式 |
| --- | --- |
| 同一份座钟记录被出示给玛丽、牧师或警方 | 线索整理仍是一份“座钟读数”；出示对象、时刻和问题在相应对话／日志中记录 |
| “向玛丽出示纸张摘录”只有出示动作，没有新信息 | 不新增证据卡；记录本次实际出示的纸张ID与对话结果 |
| 玛丽由此说明自己依据教堂报时 | 新信息以内容命名，如“玛丽的报时依据”；正文保留她的原话和来源 |
| 两条记录只是同一答复的重复拷贝 | 引用同一份已取得材料；重复问询可留对话，不重复发卡 |
| 雷丁首供与补供互相矛盾 | 分别保留版本、来源及披露先后，在对照区并列，不因语义相近而覆盖 |
| 医生初步判断与后续检查报告 | 保留不同来源、时间、确定程度和适用范围，不合并成更强结论 |
| 向警方登记材料 | 保存警方实际收到哪些材料；纯收件不新增证据，有实质核查或新说明时才形成独立内容 |

材料标题描述信息本身；详情显示来源、取得时刻及对应对话／检查。对话就近显示本次出示的材料。线索整理提供返回来源的入口，不要求玩家记住“这份证据原来是向谁出示得到的”。

开发时建立逐项清单：现有ID、正文、类别、保留／合并／转动作、替代引用、涉及的披露与前置。按作者确认后的关联处理，不通过中文标题相似度在运行时自动合并证据。

后端仍必须准确知道“谁实际接收了哪份材料”。移除重复证据卡不能移除出示记录，更不能让所有人物因为玩家持有材料就自动知情。需同步调整固定问答、模型披露、补询准备、警方登记、复盘和引用校验；新调查不得要求取得已删除的占位卡。

### 2.3 补充问询入口和提示（A批历史实现）

保留“准备条件→实际开始→取得新供述”的区分。在人物页就近展示可补问状态、已完成／未完成事项，以及开始后的当前状态；明确固定备用区是另一种操作入口。未满足条件时说明缺少哪项实际调查行为，不直接提示凶手或结论。

这一步改善入口与解释，不宣称已经解决自由问询的语义等价性。用户随后要求取消首轮／补充的独立阶段，C批按第4节替换此入口设计，不继续扩建准备清单。

### 2.4 A批验收

- 新调查不再出现时间核对表或局部算时完成门槛，原始时间材料仍可取得并引用。
- 一份证据向不同人物出示后，证据列表不重复，人物知情范围和实际回应各自保存。
- 同义重复答复不反复发卡，实质新信息与矛盾版本可区分、可引用、可追溯。
- 首供、补供、警方各项核查和正常结案仍能跑通；不需要已移除的材料ID。
- 旧修订、旧核对笔记、冻结复盘、原请求重试及真实重启恢复保持正确。

## 3. B批：入口页、案件区与调查恢复

### 3.1 页面结构

建议新增网站首页 `/`，以“进入案件区”和“继续调查”为主要入口，展示简短项目介绍。案件区 `/cases` 展示可玩案件卡片；第一版只有《牧师寓所谋杀案》，不虚构已经可玩的其他案件。

案件卡片只展示公开标题、简介、题材、玩法和可用状态。点击进入 `/cases/:caseId` 查看公开详情，再选择开始新调查或继续已有调查。后续增加案件沿用目录数据，不复制整套页面。

首页或案件区增加“我的调查”区域，列出当前身份的调查、案件名称、修订、最后活动时间及状态：调查中、推理成立待结案、已破案、已查看解答。一个案件可有多份调查，继续哪一份应明确选择；开始新调查不覆盖旧调查。

“上传我的案件”属于未来案件区的独立入口位置。B批可用简短文字说明后续支持，尚未实现时不提供可点击的假上传表单。

现有九个调查页面仍可使用原路径，增加“返回案件区”；不在这一批为统一URL重写全部页面。旧书签先恢复原调查，不能因为新增首页就新建一局。首页和案件区不显示某局的故事时钟。

### 3.2 打开网站与开始调查分离

目前 `InvestigationApp` 挂载就调用调查恢复逻辑，根路径进入现场；`OpenStudyMessage` 绑定首案，`StudyProjection` 也限制首案与修订。现有 `StartGameMessage` 虽有案件ID和修订参数，不等于已经具备公开、多案件启动能力。

B批需要：

1. 顶层区分网站页面与调查页面。仅浏览首页／目录不挂载调查恢复流程，不创建调查、不推进案件时间。
2. `cases` 服务提供公开案件目录和详情，只返回获准展示的摘要；作者真相、隐藏人物资料和完整配置不能下发。
3. `games` 服务提供本人调查摘要列表及显式开始／恢复入口。开始时由服务端验证该案件已发布、修订与场景受支持，再绑定不可变修订；不能把任意修订参数直接当作可玩权限。
4. 从当前本机演示身份恢复其本人记录。页面列表不能接受任意用户ID查询别人的调查；当前身份不包装成正式账户系统。
5. 本地只保存选中的调查定位与未决请求，调查列表和进度以服务器为准。新建仍使用稳定请求标识，丢响应不重复开局。
6. 有提交中或结果未知的请求时，先按原流程完成或恢复，再切换调查；不能丢弃原载荷。草稿按调查隔离，切换前对未提交内容明确处理，不能串到另一局。

目录、调查列表、创建与恢复接口沿用独立Message和公开Table方法；具体类名及字段在实现时对照现有协议确定，不为首页另起框架或微服务。

### 3.3 多案件的最小支持边界

案件目录采用稳定案件ID、公开摘要、发布状态及可玩修订；调查固定绑定某个修订。场景由已登记能力加载，而不是根据案件名称猜测。需梳理首案硬编码的启动、场景选择、标题、版本提示和页脚，让目录与会话读取实际案件信息。

第一版只保证登记过、验证过的案件可启动；第二个内容样例用于开发验证通用选择、知识隔离与恢复，不要求同时制作第二套大型3D。未支持的场景或能力在开始前清楚说明，不能进入后才报“不支持案件”。

### 3.4 B批验收

- 第一次打开网站停在首页，浏览案件区不产生新调查；卡片不泄露真相。
- 点击开始只创建一次，进入所选案件简介；刷新、丢响应重试不重复开局。
- 同一身份可列出并恢复多份调查，旧修订也能回到原进度，不串材料、对话、镜头或草稿。
- 返回案件区、浏览器前进后退和原有调查书签行为明确；重新进入不悄悄开新局。
- 目录新增一份受支持样例后能通过同一入口启动；未发布或不支持的内容不能绕过服务端校验。
- 案件区在窄屏可用，后端不可用时可重试并保留选中调查；完成真实重启恢复。

## 4. C批：连续问询与说法变化（2026-11-01调整）

用户最新要求：剧情连续推进，不必让玩家切换“首轮问询／补充问询”。本节替代此前围绕固定阶段推进做通用语义复核的方案。当前仍是方案，运行中的修订21尚未改变。

### 4.1 玩家看到的行为

- 每个人只有一个持续对话入口。移除新调查中的补问准备面板、完成几项的进度和“开始补充问询”按钮。
- 玩家可以直接追问和出示已有材料。人物按自己的经历、动机、正在维持的说法与实际交流回答，可以坚持、回避、解释或改变说法；不要求先按规定顺序问完固定问题。
- “首供／补供”作为历史描述可以保留，记录展示更侧重来源、内容与时间。说法改变时形成新版本，原说法仍可回看，不能覆盖成“此人一直这么说”。
- 固定备用问题用于无模型或难以复现时继续调查，与自然问询共用材料出示、说法记录和保存规则，不另设一个有特权的推进通道。
- 取得材料、向某人出示、对方回应、改变说法是不同事件。玩家拿到报告不等于人物已经收到，人物看过也不等于必须改口。

### 4.2 先做当前首案的最小实现

首轮只改现有雷丁、安妮的连续问询及其下游依赖，复用ChatCompletionClient、已有材料引用、问询预留／完成事务和历史记录。其他人物继续按本人知识回答；不在这一批建设通用的跨案件语义引擎或证据等价数据库。

模型继续承担语言理解和人物反应。默认一次调用同时返回自然答复、披露标记及必要的说法变化候选；首版不默认增加第二个独立语义裁判。具体字段在实现时结合既有协议确定，不把制作期字段名写进玩家界面。

需要完成以下修改：

1. **统一人物上下文。** 将现有分开维护的初始与补询经历、隐瞒意图、可变说法整理为本人资料及应对原则。提示词明确可以基于实际对话解释或改口，禁止自动认罪、编造取证结果或改变固定真相。加入本人实际收到的材料、已保存的说法摘要和近期对话，不能只依靠最近12轮保持长期一致；不把全案真相发给所有NPC。
2. **移除程序对新局的阶段限制。** 目前补供答复还被操作前置隐藏，人物策略也按completedOperations切换。新修订去除必须执行“开始补问”操作、收齐指定回应ID的限制，不在后台改成同一份准备清单的自动打勾版本。真正的知识权限、实际出示、检查完成和问询对象可接触性仍由后端约束。
3. **保存语义理解的结果。** 模型提出哪些话题的说法发生了变化、依据哪些实际材料；后端验证人物、作者允许的主题、引用、当前序号与请求上下文，再在原短事务中保存答复、实际出示与说法记录。陈述仍是人物说法，不因模型登记就成为客观事实。纯复述或一般澄清可只留对话，不重复发同义证据卡。
4. **固定备用共用保存路径。** 固定答复采用作者提供的内容和说明，但必须满足同样的实际材料与人物条件。点击并成功记录的固定答复本身可以形成新说法；仅展示按钮或打开人物页不能提前登记。固定入口的登记结果应能被后续自然对话理解，反之亦然。
5. **接通下游并保留旧数据。** 警方对照、阿彻联系、后续核查和结案依据实际形成的说法／材料开放，不再检查已删除的启动操作。保留需要玩家主动安排的联系、申请和核查，这些不同于内部问询阶段。发布新案件修订，旧3—21内容、冻结上下文、原请求、回执与复盘不迁移；新旧协议在边界处理。

### 4.3 为什么不只是修改提示词

提示词能让人物更自然地理解问题，也能减少手工维护两套说法的工作。当前代码却同时限制了可提供给模型的答复、策略切换和后续调查前置；只改提示词，会出现“人物已经说了新版本，系统仍认定没开始补问”的旧问题。

因此保留最小的程序职责：送入正确上下文、检查引用与权限、保存真实发生的说法变化、供后续规则读取。语义理解由模型承担，不先另建一套庞大的判断系统。结构校验无法保证正文与标记在语义上必然一致，仍需真实问法验证；若发现具体漏标或误标，先修对应上下文／提示及记录逻辑，再判断是否有必要引入额外复核调用。

### 4.4 验收范围

- 不经过任何“开始补问”按钮，能用连续对话推进到新的陈述与后续核查。
- 本案范围内同义提问、相同材料在自由和固定入口的实际出示，产生一致的知识记录与可解释的说法进展；不要求模型每次逐字相同。
- 对内容相近但不支持该主张的材料、否认、含糊回答或单纯收到报告，不误登记为已经改口。矛盾原文与后续版本都能追溯。
- 在实际对话允许的情况下，先追问后出示、先出示后追问都可自然继续，不因缺少某次固定按钮点击卡住。
- NPC只获得本人资料和实际材料，警方没有提前完成的报告，不自动发生未来认罪、抓捕或伤害事件。
- 回答超时、非法引用或结构失败时保留问题及请求，不能伪造新陈述；原请求重试不重复记录，刷新与实际重启后人物说法、材料和下游进展一致。
- 用真实TokenHub验证正例、同义改写及上述反例；模拟返回正确标记只算协议验证。完整首案及旧修订恢复仍须回归。

### 4.5 调整后的时间估算

此前估计1—2个工作日，包含更广的等价性复核设计。按本节收缩后的首案范围，目标改为**约半天给出可试玩版本，连同真实模型验收约一个工作日，约4—8小时有效开发与验证时间**，从实际开始实施计算。

| 工作 | 粗估 |
| --- | --- |
| 整理人物上下文、提示词，移除新局阶段入口与限制 | 1—2小时 |
| 连续说法登记、固定备用共用、下游引用及旧修订兼容 | 1—2小时 |
| 真实模型问法对照、边界修正、浏览器与重启回归 | 2—4小时 |

这是范围明确后的估算，不是固定钟点交付承诺；目前只调整方案，尚未开始代码实施。首轮真实模型结果用于校准剩余时间。若出现明显误标、漏标或兼容问题，说明具体原因并重估，不以只隐藏面板或放宽判定标准充当完成。任意上传案件的通用语义推进、通用证据聚类及完整案件生成不包含在此次估时内。

## 5. D批：玩家亲自发现树林线索

延续已有小型树林方案：地图提供有实际进入能力的地点入口，一段小径、一处空地和少量复用植被即可。玩家通过观察、靠近和检查发现晶体，再申请海多克辨认；专业辨认仍由警方办理，不能把外观观察升级为化验事实。

先实现第二场景的进入／返回、位置与可见范围、节点／实体／调查入口绑定及存档，再制作画面。3D与文字备用入口遵循同一规则，不以极小热点、随机掉落或装备门槛制造难度。新修订替换发现途径，旧调查中的警方查访结果和回执保留。

验收包括跨场景返回、刷新和实际重启、未检查不得获线索、重复检查不重复发卡、无WebGL备用入口及已有证词与发现结果相容。血迹等新美术仍按原决定暂缓，遗体不重新放回周五现场。

## 6. E批：用户上传案件的分阶段方案

### 6.1 先定义可玩的案件包

上传不能等同于提交一篇小说就能玩。第一版建议支持结构化JSON案件包，配套填写说明和最小样例，复用现有作者配置与校验能力。文档／自然语言到案件包的模型辅助生成属于后续能力，不作为首次上传的承诺。

案件包包含公开介绍、人物身份与各自知识、作者真相、证词与材料来源、调查入口和前提、初始状态、推理评审标准，以及受支持的场景模板引用。作者真相和私人资料只在服务端保存并按原权限投影。案件包不得指定服务器本地文件路径、任意脚本或运行时代码；首版仅选择已登记场景模板，不上传可执行3D程序。

### 6.2 草稿、校验、试玩、发布分离

1. 用户上传后先成为本人草稿，不直接进入公共案件区，也不覆盖现有案件。
2. 展示校验问题的具体字段和原因：格式、稳定ID、引用、初始可达性、前置循环、场景能力及关键调查路径。静态校验不能保证真相自洽、证词合理或模型评审公平，需另做内容试玩。
3. 校验合格后作者可私有试玩。记录所测修订，失败可回草稿调整，不能改写已有试玩调查。
4. 发布形成不可覆盖的新修订，再由目录显示。已有调查始终使用原修订；作者更新不会替换玩家进行中的内容。
5. 第一版先做本机身份下的私有导入与试玩。向其他用户公开前，再完成正式身份、作者归属和发布权限；不把当前本机凭证称为账户系统。

现有 `ImportCaseMessage(path)` 是内部文件导入，不能原样开放成用户上传接口。需要独立的内容提交边界、上传大小限制和校验结果，复用解码规则但不允许客户端传入服务器路径。具体上限根据样例体积确定。

E批分三次交付：开发样例与格式说明→本人草稿上传／校验／私有试玩→具备权限后的公开发布。各阶段界面明确支持范围。验收需覆盖失败不发布、无权查看他人草稿、公开摘要无剧透、重复上传不覆盖旧修订，以及上传内容不能改变NPC知识边界。

## 8. 实施与文档维护约定

每批先检查当前工作区及已发布修订，保留旧调查、原请求与冻结复盘。内容规则变更发布新案件修订；纯页面调整按兼容情况单独判断，不预先覆盖修订20。

测试按改动范围进行：A检查材料引用／进展及旧数据；B检查入口、身份、切换与恢复；C检查连续问询、说法记录与真实语义对照；D检查场景权限和发现路径；E检查导入、发布与资料隔离。涉及持久化时实际重启验证，不用清库或清身份掩盖问题。

每批完成后更新实现记录、交接、手动测试指南与整案流程，写明已实现、实测和仍未支持的部分。新入口页与证据整理完成后，用户应能从网站首页自行进入、恢复并跑完整案，测试不再依赖开发者口头解释哪个按钮才算真正推进。
