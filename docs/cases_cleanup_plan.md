# cases 模块职责与类型整理方案

日期：2026-10-30。基线：当前案件修订9、场景4、浏览器存档键v6。

本文记录整理方案及实施进度。用户已提出：`cases`管理范围过宽，可以精简类型。按本文分批推进，不默认启动整体重构或微服务拆分。A批实施记录见第9节，B—D批尚未实施。

## 1. 整理目标与当前判断

目标是让类型归属、案件配置和校验规则更容易理解，减少重复维护，使后续新增取证内容只需修改相关部分。验收看维护成本和边界是否改善，不以类型数与API数接近为目标。

当前`cases/objects`有41个类型文件，其中13个是ID；`cases/api`有3个消息，分别负责案件导入、旧格式导入和取得人物对话资料。玩家调查行为的主要接口在`games/api`，因此不能通过给每种类型补CRUD接口来调整数量。

本次对后端main／test源码进行了类型名引用检查：41个类型都在其他文件中出现引用，暂未发现可直接确认的孤立类型。这只是静态引用检查，不能证明每个类型的粒度都合理，也不能证明每个字段都有业务价值。删除前还需核查读写、序列化和实际规则消费者。

当前问题有四项：

1. `CaseContent`约有30个顶层字段，固定内容、场景表现、问询配置和流程前提混在一个聚合里，修改影响难以判断。
2. `FixtureLoader`同时解析完整作者文档、投影运行内容、检查引用和阶段规则；多个校验失败只得到较笼统的错误。
3. `WitnessProfile`与`DialogueDossier`重复定义知识、私人内情和对外策略三组字段，容易产生不同的限制和默认值处理。
4. `CaseRevisionTable.scala`仍导入`games.objects.*`与`games.objects.apiTypes.*`；从当前实现看没有实际使用，需要清理并用编译确认。

## 2. 模块职责与依赖方向

| 模块 | 应负责 | 不应继续承担 |
|---|---|---|
| `cases` | 作者维护的固定案件内容、修订、配置解码与完整性校验 | 玩家本局状态更新、提交请求的处理、浏览器交互状态 |
| `games` | 调查规则、会话进度、已得／已出示材料、问询阶段、时间推进及玩家视图 | 改写固定案件历史、直接访问别的服务私有工具 |
| `models` | 模型HTTP调用、供应商配置、传输错误处理 | 决定案件真相、线索权限或游戏状态变化 |
| `system` | 数据库连接／事务、共享消息和路由基础设施 | 为了消除业务依赖而堆放案件专用类型 |

推荐业务依赖保持`games → cases`。其他模块需要能力时使用公开消息或封装好的公开Table方法，不调用`private[cases]`工具。

固定配置被游戏执行器消费是正常依赖。例如核查预计耗时属于作者配置，实际受理时间和完成状态属于本局状态；前者可在`cases`，后者应在`games`。不能仅因名字中含“调查”就把固定配置全部搬到`games`。

### 特别说明：TimeAssessment暂不直接迁移

此前提出把`TimeAssessment`移到`games`，核对后发现`cases/TimeComparisonSpec`也用它保存标准判断。只迁移枚举会形成`cases → games`的业务反向依赖。

本次建议先保留现有位置，写清它是固定比较协议，供标准答案和提交输入共用。若以后迁移，必须一起重新设计标准答案与提交协议的映射，并验证JSON及原请求摘要兼容。现阶段不为移动一个类型增加第二套等价枚举、转换层或通用服务。

## 3. 类型处置清单

以下覆盖当前41个类型。每个有意义的对象仍保持独立文件；文件夹分组只改善导航，不计为类型减少。

| 类型或类型组 | 建议处置 | 原因与限制 |
|---|---|---|
| `CaseId`、`ClueId`、`EntityId`、`ExternalCheckId`、`FactId`、`OperationId`、`PersonId`、`PlaceId`、`PointId`、`RouteId`、`SceneNodeId`、`WitnessAnswerId`、`WitnessId` | 保留13个ID类型 | 有实际跨对象关联，避免同为String的编号混用。不批量改为String或类型别名 |
| `CaseRevisionRecord`、`CaseContent` | 保留；优先拆清校验职责，后续再评估聚合结构 | 修订与固定内容是必要概念；不立即改存储JSON结构 |
| `FixtureFact`、`FixtureClue` | 保留 | 事实与调查取得的信息含义不同。不能因正文相似合并，也不假设每份证词就是客观真相 |
| `FixtureNode`、`FixturePoint`、`FixtureRoute`、`FixtureOperation`、`FixtureEffect`、`EntityOpenRequirement` | 保留执行概念，按场景／调查用途分组 | 分别表达节点、入口、披露路线、操作与受支持效果；不合为充满可选字段的万能对象 |
| `CasePersonBrief`、`WitnessProfile`、`WitnessAnswer`、`DialogueDossier` | 保留；优先复用已有DialogueDossier | 公开关系、可问询资料、合法披露和私人资料有不同职责；复用内部结构不扩大公开范围 |
| `PoliceContact` | 当前保留，作为后续统一角色接入的候选 | 梅尔切特在多处特殊处理；直接删除需要同时调整角色识别、资料、路线、警方视图和历史上下文，超出首批范围 |
| `SceneObservation`、`SceneObjectBinding` | 当前保留，核对登记重复后再决定是否局部收拢 | 一个描述可见外观，一个绑定实体及操作。没有交互实体的外观节点也可能合法，不能强制两者一一对应 |
| `AreaMap`、`MapLocation`、`MapRoad` | 保留 | 地图、地点和道路各有独立数据结构与消费者；不改为无字段名元组或任意Map |
| `InvestigationClock`、`ExternalCheckSpec`、`InvestigationStage`、`TimeComparisonSpec`、`TimeAssessment` | 固定配置当前留cases；运行状态留games | 保持案件定义与会话状态分离，避免为减少cases文件数制造循环依赖 |
| `WitnessFollowUpSpec` | 保留 | 表达开始操作、本人物证接收、关键回应和阶段策略；不能丢掉实际出示与实际回应的区别 |
| `StatementComparisonSpec`、`StatementComparisonRowSpec` | 保留，检查是否重复记录可推导关联 | 行标签与两版本线索ID有明确含义；单一消费者并不等于该类型多余 |

### 首个具体精简点：复用DialogueDossier

当前结构示意：

```text
WitnessProfile：knowledge、privateContext、policy
DialogueDossier：knowledge、privateContext、policy
```

推荐候选结构：

```text
WitnessProfile：其他现有字段 + dossier: DialogueDossier
```

复用已有类型，减少重复字段声明及校验，不新增另一种等价档案类型。`WitnessFollowUpSpec`只有当前阶段的知识与策略，没有私人真相，不能为复用而补一个空privateContext并覆盖原私人资料。

实施前必须检查`GetDialogueKnowledgeMessage`、`InterviewRules.context`和已冻结`InterviewContext`的组合规则。保留静态资料与本轮阶段策略的现有优先关系，不因整理结构改变模型知道的内容。

内部改为嵌套字段时，现阶段采用显式codec保持现有扁平存储形状和缺省行为；旧JSON仍可解码，新旧语义值相等。`WitnessProfile`不能直接作为公开响应发送，仍经明确的玩家视图投影。

这一项减少的是重复定义和维护点，不减少独立类型总数。当前没有证据支持承诺“41个立即删成某个数字”；后续若确认类型可以移除，逐个记录真实消费者与替代关系。

## 4. 目标目录与CaseContent处理

先按用途组织`cases/objects`，候选分组为：

```text
cases/
├── api/                    保留现有公开消息，不补无业务用途的接口
├── objects/
│   ├── [各现有ID类型]       保持稳定导入位置，降低迁移影响
│   ├── CaseContent.scala
│   ├── CaseRevisionRecord.scala
│   ├── content/            事实、线索、公开人物信息
│   ├── scene/              节点、物品绑定、公开外观、地图
│   ├── dialogue/           人物资料、披露配置、补充与对照配置
│   └── investigation/      路线、操作、条件、阶段、时钟和核查定义
├── tables/CaseRevisionTable/
└── utils/                  源文档加载和服务内部校验
```

这是候选组织方式，不要求立刻移动全部文件。先处理一组类型和所有显式引用，编译通过后再推进下一组；不要同时做包迁移、字段变化和序列化变化。

首批保留`CaseContent`当前数据形状。通过明确的校验函数和分组文档先改善职责，不为了让根对象字段少就新加多层包装。

后续若调用方确实总是成组使用场景配置或对话配置，再提取对应聚合；届时单独说明收益、codec和旧存储适配。聚合类型数可能增加，不能把“根字段少了”包装成“类型精简”。避免保留新旧两套长期并行的CaseContent。

## 5. 校验整理方式

先在`FixtureLoader`内按职责提取有名称的纯函数；只有文件确实仍难以阅读时才拆成少量服务内部文件。

| 校验职责 | 典型规则 |
|---|---|
| 基础引用与场景 | ID唯一、父链无环、入口节点存在、道路端点有效 |
| 调查执行 | 操作目标存在、前提引用有效、披露材料存在 |
| 对话与阶段 | 人物归属、本人所需证据、关键路线可达、补充路线阶段限制 |
| 核查与比较 | 耗时范围、结果不可提前从普通路线取得、对照行归属 |

继续保留`FixtureLoader.valid(record): Boolean`作为当前Table等调用方的兼容入口，内部使用能定位配置路径／对象ID的校验结果。不要新增“校验服务→转发层→原校验”这样的空层。

错误示意：`investigation.followUps[0].requiredRoutes：route_x不属于该人物`。错误中不输出私人资料正文、密钥或完整模型上下文。

不要把“引用完整性检查通过”宣传成“案件推理逻辑必然正确”；后者仍需内容审查和实际验收。

## 6. 分批实施与验收

### A批：整理依赖和校验，建议先实施

改动：清理已核实无用的跨模块导入；在原文件内拆分配置校验；保留公开函数签名、JSON结构和全部类型；错误增加明确对象定位。

验收：现有合法案件继续通过；非法引用、阶段死锁、人物归属错误被拒绝且错误可定位；新增针对实际缺口的配置反例测试。运行后端测试。本批不改前端，无需浏览器全量回归或真实付费模型抽查。

完成标准：依赖更清楚、校验更容易维护；类型数量可能仍为41，不以此判失败。

### B批：复用人物资料结构

改动：先为旧人物JSON及冻结问询上下文建立兼容样例，再将`WitnessProfile`内部三组资料收拢为已有`DialogueDossier`；显式保持旧codec形状，统一重复校验。若影响显著超出该结构，保留旧实现，另列阻碍，不扩成全面角色重构。

验收：旧／新缺省字段解码一致；同修订重复导入判等；阶段切换保留私人真相；旧未决问询和原回执继续有效；公开快照不含privateContext／policy。运行后端相关测试和人物／补充问询浏览器用例，不因类型重排自动调用真实模型。

### C批：按已确认职责组织类型

改动：按第4节逐组调整目录／包与明确导入，保留13个ID的稳定位置。每次只迁移一个相关组；不将case配置随意转移到games，也不新增网络服务。

验收：编译与后端完整回归通过；数据codec、端点和响应格式保持不变；前端类型／生产构建通过。用已有代表性存档验证旧版本恢复，不清空用户数据。

### D批：有证据后再删除或统一

候选：警方与普通问询角色资料的共同部分、场景外观与实体登记重复信息、CaseContent成组配置。每项先列消费者、能消除的重复和替代结构；若删除引入更多可选字段、转换或重复状态，就不做。

该批不预先承诺全部实施，不阻塞枪接触者、纸张原件与视线复验等主线功能。删除真正有用的语义类型不能作为完成指标。

## 7. 兼容与实施边界

- 改动前检查工作区并保存／推送用户已有成果；保留当前课堂文档及交接修改，不覆盖其他工作。
- 不修改案件修订3—9的语义，不为结构整理新建剧情版本；场景4、v6存档键和路由保持。
- 当前数据库`case_revisions.body_json`保存案件，问询请求保存冻结上下文；两者都必须兼容。旧字段缺省、枚举字符串和原请求摘要参与的JSON形状不能随手改变。
- 同一修订重复导入比较解码后的内容。若结构调整让旧记录与当前源文档不再判等，必须修复适配，不覆盖旧修订掩盖问题。
- 无数据库删表、清库、旧回执重写或对话重生成；暂不需要表结构迁移。
- 案件结构、公开DTO和完整作者源文档具有不同权限／用途，不能为了复用直接把完整对象发给浏览器。
- 若确有无法无损兼容的存储变化，停止该项结构修改，先单独写明迁移方案与收益；不扩展原任务默认执行。

## 9. A批实施完成（2026-10-30）

修改前已提交并推送课堂文档、交接记录及本方案，基线为`2ec91e9`。本批仅整理案件校验和无用导入，B—D批未实施。

- `FixtureLoader`保留`decode`与`valid(record): Boolean`入口，增加服务内部`validation(record): Either[String, Unit]`。将整串布尔条件拆成基础信息、场景、线索、人物、执行、阶段、核查、地图、补充问询、供述对照10组纯校验函数；共用少量遍历、唯一性及条件辅助函数，没有新增领域类型。
- 校验逐项返回首个失败路径，例如`scene.nodes[0].parent`、`investigation.followUps[0].requiredRoutes`。作者数组解码补充所属数组及索引；完整作者文档专属的实体／地点关联检查仍在加载阶段。未扩大原执行协议或更改合法配置的含义。
- `CaseRevisionTable`删除对`games.objects`、`games.objects.apiTypes`及无用JDBC类型的导入；插入及读取复用上述详细校验，便于定位错误存储内容。SQL仍封装在原Table中。
- 新增`FixtureValidationSuite`的7项测试，覆盖最小／正式配置及存储codec往返、父链循环／缺失、重复ID／未知事实／错误读路线、人物归属／阶段自依赖、私密正文不回显、时钟／报告绕过／地图／对照错误，以及源数组索引。
- 原生Windows后端完整测试91项通过（原84项＋新增7项），含既有旧修订、存档、回执、问询隔离及HTTP流程回归。没有运行前端浏览器全量测试或调用真实付费模型，本批未涉及这些路径的协议／界面变化。

领域类型仍为41个；案件内容、JSON编解码定义、数据库结构、旧存档、原请求摘要格式、场景4和v6键均未修改。下一批按第6节处理人物资料结构复用，需单独验证旧冻结上下文和扁平codec兼容。
